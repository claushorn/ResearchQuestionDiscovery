# Frontend Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A local web app (`uv run frontend`) that shows every stage's results, lets the user triage and select
items, and runs the next stage on the selection as an *Agent Task* (the existing CLI command in the background).

**Architecture:** New package `Frontend/frontend` (FastAPI + Jinja2 templates + htmx, vendored; no JS build).
Pages read the stages' own stores through read-only *view* functions in `frontend/views.py` that call the stages'
own loaders and checks. Runs are subprocesses of the existing CLIs managed by `frontend/tasks.py`; the
frontend's own data (triage, task log) is one SQLite file in git-ignored `Frontend/data/`.

**Tech Stack:** Python 3.12, FastAPI, Jinja2, uvicorn, htmx (vendored static file), SQLite, pytest + FastAPI
TestClient.

**Spec:** `docs/superpowers/specs/2026-10-01-frontend-design.md`

## Global Constraints

- No stage logic in the frontend: runs are the existing CLI commands; derived statuses use the stages' functions.
- Read-only towards stage records; the frontend writes only `Frontend/data/` (git-ignored, in the repo-layout guard).
- Bind to `127.0.0.1` only.
- Every deliberate failure shown in the UI carries the stage's message and fix (`RqdError.fix`); no traceback pages.
- One Agent Task at a time; Run is disabled while a task (or an outside CLI run holding the lock) is active.
- The run log is named **Agent Tasks** everywhere in the UI.
- Tests prefixed `test_fe_*.py`, helper module `fe_testing.py`; `uv run` everywhere; atomic commits.

## Review Focus

1. 500+ problems: Problems table must filter / sort / page server-side and render in < 1 s on the real store.
2. A malformed record in one stage must not break the page: listed with message and fix, other rows still shown.
3. Cancelling a task mid-run leaves the stage's records consistent (only finished items written) and releases the lock.
4. A CLI run started in a terminal while the UI is open: UI shows "busy (outside run)", Run disabled, no second run.
5. Confirmation's refused-items list matches what the CLI actually refuses (same check functions, not a copy).

### Task 1: Stage checks callable without an agent client

Make the pre-spend checks and staleness reusable on stores alone (no duplication in the frontend).

**Files:** Modify `OpportunityGenerator/opportunitygenerator/run.py`, `EconomicValueInvestigator/economicvalue/assess.py`,
`ChallengeInvestigator/challengeinvestigator/run.py`; tests in each package.

**Interfaces — Produces:**
- `opportunitygenerator.run.OGStores(problems, fits, investigations, assessments, opportunities)` (dataclass of
  `YamlStore`s, built by `OGStores.open(paths, cfg)`); `load_inputs(stores, pid)` and `stale_inputs(stores, record)`
  take it; `OGContext` holds `stores` (callers migrated, no second variant left).
- `economicvalue.assess.gate(problems, investigations, problem_id, force) -> str` (stores instead of the context).
- `challengeinvestigator.run.refusal(store, challenges, item_id, force) -> str | None` (None = runnable, else the
  reason); `investigate()` uses it.
- Behaviour unchanged: all existing tests pass unmodified except for the changed call signatures.

**Tests first:** each new signature callable with stores only (no client/fetcher); a refused case returns /
raises the same message as before.

### Task 2: ProblemExtractor `--candidate`

**Files:** `ProblemExtractor/problemextractor/{extract,cli}.py`, `ProblemExtractor/tests/test_pe_extract.py`.

**Interfaces — Produces:** `run_extraction(ctx, client, limit=None, categories=None, candidate_ids=None)`;

**Interfaces — Produces:**

  challengeinvestigator, personalfit, opportunitygenerator})`, `load_config(path)`.
- `create_app(root: Path) -> FastAPI`; `uv run frontend [--port]` starts uvicorn on 127.0.0.1 and opens the browser.
- Base layout: nav `Overview · Candidates · Problems · Opportunities · Challenges · Agent Tasks`, task panel slot.

**Tests first:** app serves `/` with the nav (TestClient); binding host is 127.0.0.1; a missing stage directory
shows a clean configuration error page with the fix.

### Task 4: Views — read the stages' stores

**Files:** `Frontend/frontend/views.py`, `Frontend/tests/test_fe_views.py` (fixture stores built with the stages'
test helpers / minimal records).

**Interfaces — Produces** (pure functions over the stores; each returns rows + `errors: list[(file, message, fix)]`):
- `candidates(roots, filters, page)` — source, category, tier, statement, payment, deadline / due passed,
  processed → problem_id (ProblemExtractor state).
- `problems(roots, filters, sort, page)` — funnel columns: sources / best tier, novelty status, value range, fit
  score, OPP id + recommendation, stale flags (via `personalfit.run.is_stale`, `opportunitygenerator.run.stale_inputs`).
- `dossier(roots, problem_id)` — candidates → problem → novelty → EV → fit → opportunity, with evidence and
  verification.
- `opportunities(roots, filters, page)`, `brief(roots, opp_id) -> str`, `challenges(roots, filters, page)`,
  `challenge(roots, item_id)`.
- `overview(roots)` — per stage count / waiting / stale.

**Tests first:** each view on fixtures; waiting / stale derivation equals the stages' own functions; a malformed
record appears in `errors` while the others are returned (Review Focus 2); 600 synthetic problems filtered /
sorted / paged correctly and fast (Review Focus 1).

### Task 5: Triage

**Files:** `Frontend/frontend/db.py` (SQLite: `triage`, `tasks`), triage routes + partial template, tests
`Frontend/tests/test_fe_triage.py`.

**Interfaces — Produces:** `Triage.set(kind, item_id, status: shortlist|reject|none, note)`, `Triage.get_many(kind,
ids)`; views accept a `triage` filter; triage controls on every table row and the dossier (htmx, no page reload).

**Tests first:** set / clear / note round-trip; filter "shortlisted" / "not rejected"; stage records untouched
(file hashes before / after).

### Task 6: Pages

**Files:** templates `candidates.html`, `problems.html`, `dossier.html`, `opportunities.html`, `brief.html`,
`challenges.html`, `challenge.html`, table / filter partials; routes in `app.py`; tests `Frontend/tests/test_fe_pages.py`.

**Interfaces — Consumes:** Task 4 views, Task 5 triage. **Produces:** pages per spec §5 with checkbox selection
and the next-stage action buttons (wired in Task 7).

**Tests first:** each page renders fixture data (key fields present); filters and paging via query parameters;
errors section shown when a record is malformed; brief rendered from `briefs/OPP-NNNN.md`.

### Task 7: Agent Tasks

**Files:** `Frontend/frontend/tasks.py`, `actions.py`, templates `confirm.html`, `task_panel.html`,
`agent_tasks.html`; tests `Frontend/tests/test_fe_tasks.py`.

**Interfaces — Produces:**
- `ACTIONS`: per page the next-stage actions → CLI command line (`problemextractor run --candidate …`,
  `noveltyinvestigator investigate …`, `economicvalue assess … [--force]`, `fit assess …`,
  `opportunities generate …`, `challenges headroom …`, `challenges investigate … [--force]`), the stage config's
  per-item budget cap, and a `check(roots, item_id, force) -> str | None` that calls Task 1's functions.
- `confirm(action, ids, force)` → count, cap, worst case, refused items with reasons.
- `TaskRunner.start(action, ids, force) -> task_id` (subprocess of the stage's console script in the same venv,
  output to `Frontend/data/tasks/<id>.log`, row in `tasks`), `status(task_id)` (per-item results parsed from the
  shared `[tag i/n] id -> …` lines; failures with reason), `cancel(task_id)` (terminates the process group),
  `busy() -> None | reason` (own running task, or the stage's run lock held by an outside run).
- Task panel polls status (htmx every 1 s) while a task runs; Agent Tasks page lists tasks.

**Tests first (fake console scripts printing the real line format):** start → streamed lines → per-item results;
failure lines parsed with reason; cancel stops the process and records `cancelled` (Review Focus 3); a held lock
→ `busy()` reason and Run disabled (Review Focus 4); refused list equals Task 1 checks (Review Focus 5); a second
start while busy → refused.
